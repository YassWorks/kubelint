## Decisions
- Engine: `Linter::lint` parses and runs per-object rules, KL0001, KL0003 and suppression
  filtering per file in parallel (`lint_file`); `check_all` rules then run once, and
  their findings are filtered with the suppressions of the file they point into. A test
  compares an 8-thread run with a 1-thread run.
- ADR 0013 (JSON): `{version: 1, diagnostics, summary}`; positions are `line`, `column`
  (1-based, UTF-8 bytes) and `offset`; no timing; adding fields is not breaking.
  User docs live in the new `docs/user/output-formats.md`.
- ADR 0014 (SARIF): one run, every built-in rule listed (stable `ruleIndex`), `info` is
  `note`, help appended to the message, UTF-16 columns, relative paths with `%SRCROOT%`,
  absolute paths as `file:` URIs, no `originalUriBaseIds`.
- ADR 0015 (GitHub): `::error`/`::warning`/`::notice`, title `code name`, UTF-16
  columns, summary line without timing at the end.
- M2-10 uses a 30-line Levenshtein function (`kubelint_linter::did_you_mean`) instead of
  `strsim`, per the "under about 50 lines" dependency rule. Threshold: one edit per three
  characters, case-insensitive. `SelectionError` has a new `suggestion` field.

## Problems
- The GitGuardian check (a third-party app) runs on most commits but finishes minutes
  after `ci-success`, and did not run at all on #37's head commit. I waited for every
  listed check to complete before merging. `wait-all.sh`-style polling (all check runs
  completed, not just `ci-success`) is the safe approach.
- Inline `insta` snapshots with `@""` still fail without `cargo-insta`; switched one CLI
  test to a file snapshot again. An inline snapshot written by hand from known output
  worked first time.
- Working on the next task on a local branch while CI ran, then `git stash -u` and reset
  the session branch onto the new `main` after the merge, worked well and saved time.
